# 逐章差異

四支 lab 各自完整、不共用任何模組，所以「看得出全貌」這件事由這份文件負責。

每支檔案的段落順序都一樣，直接 diff 就能看到差在哪：

```bat
fc labs\lab1_detect.py labs\lab2_loop.py
fc labs\lab2_loop.py   labs\lab3_tello.py
fc labs\lab3_tello.py  labs\lab4_patrol.py
```

固定的七個段落：

```
1. 參數    2. 載入模型    3. 影像來源    4. 推論
5. 畫框    6. 存檔        7. 主迴圈
```

## lab1 → lab2：從一疊照片到一條影像流

**新增**

- 段落 3：`open_source()` 回傳 `(cap, fps)`；`read_frame(cap, loop)` 處理播完循環
  - `cap.set(cv2.CAP_PROP_BUFFERSIZE, 1)`：只留最新一格
  - 純數字的 `--source` 當鏡頭編號
- 段落 5：多一個 `draw_status()`，把狀態列畫在畫面下緣
- 段落 6：存檔多了 `--threshold` 與 `--cooldown` 兩個條件
- 段落 7：
  - `for path in files` → `while True`
  - `--every N`：只有 `idx % every == 0` 的幀才跑模型
  - 鍵盤：`q` 離開、`p` 拍一張
  - `cv2.waitKey(delay_ms)` 照影片 fps 節流
  - `try / except KeyboardInterrupt / finally`

**改寫**

- 語意整個反過來：lab1「一張不漏」→ lab2「處理不完就丟掉」
- 摘要多了「推論幾幀 / 跳過幾幀 / 整體 fps」

**拿掉**

- `--reload-each`（那是 lab1 用來量載入成本的教學開關，任務已完成）

## lab2 → lab3：從影片檔到真的無人機

**新增**

- 段落 3 整段換掉：
  - `open_tello()`：`Tello()` → `connect()` → `streamon()` → `get_frame_read()`
  - `read_frame()`：**`cv2.cvtColor(frame, cv2.COLOR_RGB2BGR)`** —— djitellopy 給的是
    RGB，cv2 全家吃 BGR
  - `close_tello()`：rc 歸零 → 需要就降落 → `streamoff` → `end()`
  - 第一格畫面等 10 秒就放棄（`FIRST_FRAME_TIMEOUT_S`）
- 段落 7：
  - 狀態列每秒讀一次電量與高度（讀快取，不送指令）
  - 飛行鍵：`T` / `L` / 空白 / 方向鍵 / `W S A D` / `X`
  - **rc 節流 50 ms**（`RC_INTERVAL_S`），不能每幀都送
  - `finally` 裡會降落
- 三個安全常數：`RC_INTERVAL_S`、`STATE_INTERVAL_S`、`FIRST_FRAME_TIMEOUT_S`
- 方向鍵用 `cv2.waitKeyEx`（`waitKey` 只回低位元組，吃不到方向鍵）

**新增的參數**

`--speed`、`--preview-only`、`--no-land-on-exit`、`--allow-emergency`

**行為上最重要的三個新規則**（細節見 [03-lab3.md](03-lab3.md)）

1. 沒看到畫面就按 `T` → 印訊息、取消起飛，不代開串流
2. 空白鍵 / `L` / `Q` 是三件不同的事
3. `finally` 一定收乾淨；CLI 預設離開時自動降落

**拿掉**

- `--loop`（無人機沒有「播完」這件事）

## lab3 → lab4：三種來源，一支工具

**新增**

- `Source = namedtuple("Source", "kind handle fps is_live extra")`
- 段落 3 的三個函式各有一組 `if kind ==` 分支：
  `open_source()` / `read_frame()` / `close_source()`
- 段落 6：存檔條件依 `source.is_live` 分岔
  ```python
  should_save = run_now and (
      not source.is_live or args.save_all
      or (best > args.threshold and 過了冷卻))
  ```
- 段落 7：
  - 啟動時**印出生效的語意**（有限來源 / 即時來源）
  - `read_frame()` 的第三種回傳值 `"wait"`（Tello 還沒吐第一格）
  - 只有 `source.kind == "tello"` 才進飛行鍵那一段
  - `=== 摘要 ===`：讀幾幀、推論幾幀、平均延遲、整體 fps、存幾張
- `--dry-run`：不載模型、不寫檔，整條流程照走（可當回歸測試）
- `--save-all`：即時來源也每張都存（不看門檻）

**合併**

lab1 的「一張不漏」與 lab2/lab3 的「丟得起就丟」在這裡共存，由 `--source` 決定。
不做成 `--drop-stale` 開關的理由見 [04-lab4.md](04-lab4.md)。

## 重複了什麼（以及為什麼可以接受）

這四段程式碼在四支檔案裡各有一份，內容幾乎一樣：

| 重複的東西 | 行數 | 四支檔案裡的差異 |
|---|---|---|
| `load_model()` | ~10 | 完全一樣 |
| `detect()` | ~12 | 完全一樣 |
| `draw()` / `_color()` / `COLORS` | ~25 | 完全一樣 |
| `open_run()` / `save()` | ~30 | 完全一樣 |

加起來每支檔案約 80 行是重複的。**這是刻意的。**

抽成 `crackkit\detector.py` 之類的共用模組，換來的是：
學生讀 `lab3_tello.py` 時，看到 `from crackkit import detect` 就得跳到另一個檔案，
而那個檔案裡又有為了四支通用而多出來的參數與分支。**教材的第一要務是可讀，不是
DRY。**

那什麼時候該抽？當你要改一個共同行為、而且得改四次的時候。那個痛點是真的，
但它屬於「維護一個長期專案」的課，不屬於「三節工作坊」。

> 業界的判斷標準通常是「重複三次才抽」（rule of three）。我們這裡是四次還不抽，
> 因為讀者是第一次看這段程式的人 —— **抽象的成本由讀者付，不是由作者付。**
