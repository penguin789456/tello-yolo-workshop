# 設計決策：七個「為什麼」

這份是整套教材最重要的一份文件。

程式碼會告訴你「怎麼做」，但不會告訴你「為什麼不用另一種做法」。下面七條每一條都是
**常見做法 → 會出什麼事 → 這份教材怎麼做**，而且每一條都附一道你可以自己跑的指令。

---

## 1. 模型只載入一次

**常見做法：** 每處理一張圖就 `YOLO(weights)` 建一次模型。

**會出什麼事：** 每張圖都要重新把權重從磁碟載進來、重建網路。小模型幾百毫秒，
大模型好幾秒。使用者會以為程式壞了。

**這份教材：** 模型在迴圈**外面**載入一次，並跑一張假圖 warmup。

```python
model = YOLO(weights)
model.predict(np.zeros((640, 640, 3), np.uint8), verbose=False)   # warmup
```

這一支程式把載入放在主迴圈**之前**，所以啟動時會印一行：

```bat
python labs\lab3_detect.py --source video --path data\samples\test.mp4 --headless --max-frames 10 --snap-every 5
python labs\lab3_detect.py --source video --path data\samples\test.mp4 --headless --max-frames 10 --snap-every 5
```

```
模型載入 + warmup：3015 ms（之後按 P 不用再等）
```

3 秒。如果把 `YOLO(weights)` 搬進按 `P` 的那段程式裡，你每次按都要等這 3 秒 ——而那時候飛機還在空中。

**warmup 為什麼也要做：** 第一次推論要付 lazy 初始化的成本（配置記憶體、建 kernel）。
不 warmup，第一張圖的延遲會是後面的好幾倍，你量出來的平均值就沒有意義。
實測第一張 89 ms、後面每張約 52 ms —— 差了快一倍。

## 2. 前處理要和訓練時一致

**常見做法：** 自己先把影像縮到想要的大小，再丟給模型。或者沒注意色彩通道順序。

**會出什麼事：** 模型**不會報錯**，只會安靜地變爛。

兩個最常見的：

- **自己先 resize。** `ultralytics` 內部會自己做 letterbox 到 `imgsz`。你先縮一次、
  它再縮一次，等於縮兩次，小目標直接消失。**把原圖給它就好。**
- **RGB / BGR 搞反。** `cv2` 全家吃 **BGR**，但很多來源給的是 **RGB** ——
  `djitellopy` 的 `frame_read.frame` 就是 RGB。不轉的話畫面顏色會反過來
  （天空變橘色），而且送進模型的張量跟訓練時不一致，分數會怪。

`lab2_capture.py` 與 `lab3_detect.py` 因此都有這一行，拿掉就會出事：

```python
return cv2.cvtColor(frame, cv2.COLOR_RGB2BGR)
```

**可以帶走的原則：** 前處理和訓練時不一致，模型不會報錯，只會安靜地變爛。
這種 bug 最難抓，因為程式「看起來能跑」。

## 3. 畫面不要被模型綁住

**常見做法：** 主迴圈裡每抓到一幀就送進模型，畫面等推論跑完才更新。

**會出什麼事：** 實測 CPU 上 `yolo26n` 一張要 **50~60 ms**，所以畫面會被壓到
15~20 fps；換成大一點的模型可能只剩 1 fps 以下。**那個更新率沒辦法操控無人機** ——
等你從畫面看到障礙物，早就撞上了。

更糟的是如果你改用「把每一幀排進佇列慢慢消化」：推論比抓幀慢，佇列越積越長，
**延遲一路累積**，跑幾分鐘之後你看到的是十幾秒前的畫面。

**這份教材：** 主迴圈**完全不碰模型**。畫面以來源原本的速度跑，只有你按下 `P` 才對
那一張跑一次 YOLO。

```python
# 主迴圈裡沒有 detect()。整支程式唯一跑模型的地方：
if key in (ord("p"), ord("P")):
    snap(model, frame, run_dir, args.conf, idx)
```

這樣一來，那些「要不要丟幀」「每幾幀推論一次」的參數**根本不需要存在**。

另外兩個細節讓畫面不會積延遲，而且都不用自己寫執行緒：

- Tello 的 `frame_read.frame` **本來就是「最新一格的快照」而不是佇列**，讀它永遠拿到
  最新的（`djitellopy` 內部那條解碼執行緒幫我們做了這件事）
- `cv2.VideoCapture` 沒有這個性質，所以 `--source video` 那條路加了
  `cap.set(cv2.CAP_PROP_BUFFERSIZE, 1)`，叫解碼器少存舊幀

**可以帶走的原則：** 先問「這個東西需不需要即時」。不需要的話，把它從主迴圈裡拿出來，
你會同時省掉效能問題和一整組參數。

**摘要裡「跳過 48 幀」不是缺陷，那是設計。** 內附的 `test.mp4` 每一幀右下角都印了幀號，
所以不加 `--headless` 跑的時候，你會直接看到它跳過哪幾號。

## 4. 本機優先存檔，迴圈裡不碰網路

**常見做法：** 偵測到東西就在迴圈裡上傳圖床、發通知。

**會出什麼事：** 網路一慢，整條偵測管線跟著卡住。上傳失敗還可能讓結果直接消失 ——
根本沒存到本機。

**這份教材：** 命中就先寫進 `runs\<時間戳>\`，**迴圈裡永遠不碰網路**。要不要上傳、
傳到哪裡，是事後另一個步驟的事。整份教材因此**零金鑰、零網路呼叫**。

**索引為什麼用 `index.jsonl` 而不是一包 `.json`：** jsonl 是一行一筆、用 append 寫入。
程式被 `Ctrl-C` 或斷電，已經寫進去的行仍然是合法內容；整包 json 則會因為缺一個 `]`
而整個檔案讀不出來。

```bat
type runs\20261002_195928\index.jsonl
```

## 5. 會產生副作用的動作不要自動觸發

**常見做法：** 偵測到就自動存檔、自動發通知。

**會出什麼事：** 即時來源一秒好幾幀，對著同一個目標幾秒內就存出幾百張幾乎一樣的圖
（換成發通知就是把訊息配額打爆）。接著你就得加一堆參數來擋：多高的分數才算命中、
至少間隔幾秒才能再存一次……

**這份教材：** **存檔只在你按下 `P` 的時候發生。** 沒有自動存檔，所以不需要門檻，
也不需要冷卻。

```python
if key in (ord("p"), ord("P")):
    snap(model, frame, run_dir, args.conf, idx)   # 拍照 + 辨識 + 存檔
```

這也讓程式的行為好解釋得多：按幾次 `P`，`runs\` 裡就有幾張圖、`index.jsonl` 就有
幾行。**不會有「我沒做什麼它自己就存了一堆」的情況。**

> 真要做自動存檔也不是不行，但那時候你就得把門檻和冷卻一起加回來 —— 而且要先回答
> 「多高才算命中」這個沒有標準答案的問題。
> [92-課後練習.md](92-課後練習.md) 有一題就是這個。

**可以帶走的原則：** 會對外面世界產生副作用的動作（寫檔、發訊息、花錢、起飛），
不要放在自動迴圈裡。讓使用者明確說「現在做」。

## 6. 不可逆的動作不能是副作用

**常見做法：** 按下「起飛」時，如果影像串流還沒開，程式就順手幫你打開，然後起飛。

**會出什麼事：** 起飛是**不可逆的實體動作**。它不該是別的操作的副作用，也不該在前置
條件沒滿足時「自動幫你補齊」。沒有畫面就起飛 = 盲飛。

**這份教材：** 還沒收到任何一幀畫面時按 `T`：

```
尚未看到畫面，取消起飛。沒有畫面等於盲飛。
```

**印訊息、中斷操作，不代勞。**

另外兩個同類的決定：

- **緊急停止（切斷馬達，機體直接墜落）預設沒有按鍵。** 要加 `--allow-emergency`
  才會啟用 `X`。
- **離開程式時自動降落**（`--no-land-on-exit` 可關）。這一條和前面兩條看起來矛盾 ——
  降落不也是程式擅自做的嗎？差別在**有沒有人看著**：有 GUI 的程式關窗時可以彈窗問
  使用者，CLI 程式一結束就沒人控制飛機了，懸停到電池耗盡然後掉下來更糟。

  **同一個原則在不同介面下會導向不同結論 —— 這正是為什麼要懂原則，不是背規則。**

## 7. 停止的語意要分開

**常見做法：** 一個「停止」按鈕。

**會出什麼事：** 沒人說得清它到底停了什麼。使用者以為按了會降落，結果只是停止分析、
飛機還在空中懸停。

**這份教材：** 三件事就是三件事：

| 動作 | 做什麼 | 不做什麼 |
|---|---|---|
| 空白鍵 | 四軸速度歸零（懸停） | 不降落、不斷線 |
| `L` | 降落 | 不斷線、不離開程式 |
| `Q` | 離開程式（預設會先降落） | — |

而且不管你怎麼離開（`Q`、`Ctrl-C`、程式炸掉），`finally` 都會走完：
rc 歸零 → 需要就降落 → `streamoff` → `end()`。

**可以帶走的原則：** 一個動作對應一個明確的結果。把三件事塞進一個按鈕，使用者一定會
誤解，而誤解的代價是一台飛機。

## 誠實的限制

教材要對自己的邊界誠實，這也是開發流程的一部分。

### COCO 預訓練權重只認得 80 類，而且它會硬給你答案

`yolo26n.pt` 認得 `person` `bottle` `cup` `book` `scissors` `cell phone` `laptop`
`mouse` `keyboard` 那 80 類。**沒有 `pencil`、沒有 `pen`。**

重點是：**模型不會說「我不知道」。** 只要你把門檻放低，它就會從 80 個既有類別裡
挑一個最像的給你。內附的 `data\samples\` 是合成的幾何圖形（圓形、方塊、三角形），
COCO 裡當然沒有這些類別。實測：

```bat
python labs\lab3_detect.py --source video --path data\samples\test.mp4 --headless --max-frames 10 --snap-every 5
:: 預設 --conf 0.25：8 張全部 0 處。模型沒亂講。

python labs\lab3_detect.py --source video --path data\samples\test.mp4 --headless --max-frames 10 --snap-every 5 --conf 0.05
:: 降到 0.05：冒出 9 個框，orange ×6、bicycle ×2、tv ×1，最高分 0.17
```

**你畫的是圓形，它硬要說那是橘子。** 但注意它的分數只有 0.17 —— 它自己也沒把握，
是你把門檻放得太低。**門檻只能決定它多敢講，決定不了它懂不懂。**

> 想看「模型世代的差別」，自己抓一顆舊的對照：
> `python -c "from ultralytics import YOLO; YOLO('yolo11n.pt')"`，然後
> `--weights yolo11n.pt`。實測舊模型在**預設門檻下就會冒出 3 個框**
> （sports ball、kite，最高 0.32）—— 新模型保守得多，而這是可以量的。

要辨識你真正要的東西，只有一條路：收集那個東西的照片、標註、訓練一顆新權重。
**但換上去只要改 `--weights models\best.pt`，這三支程式一行都不用動** ——
那是介面設計對了的證據。

### 其他

- **訓練不在這個工作坊的範圍。** 100 分鐘裡標註、切分、超參數、mAP 判讀隨便一項都
  塞不進來。想接下去的話，`ultralytics` 的 `yolo train` 是起點。
- **飛行操控沒有在真機上驗證過。** 開發環境沒有 Tello。鍵盤對應、安全規則、收尾流程
  都寫好也讀過，但真機的起飛／降落反應沒實測。首飛檢查表在 [01-lab1.md](01-lab1.md)。
- **`cv2.waitKeyEx` 的方向鍵回傳值不跨平台。** 程式裡寫的是 Windows 的值，所以另外留了
  `8/2/4/6` 當備援。函式庫的回傳值不保證跨平台，這種東西要留退路。
- **`ultralytics` 是 AGPL-3.0。** 課堂使用沒問題；作品要散布之前請看授權條款。
