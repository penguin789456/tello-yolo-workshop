### 為什麼用 `--preview-only`

`--preview-only` 完全不載模型、不推論。三個理由都很實際：

- **預覽不需要模型。** 只是要看畫面時，不該先等 YOLO 和 PyTorch 載入。
- 只是要看畫面的時候，不該先等模型載入好幾秒。
- CPU 上 `yolo11n` 推論約 10~25 fps，換更大的模型可能只剩 1 fps 以下。
  **那個更新率沒辦法操控無人機** —— 等你從畫面看到障礙物，早就撞上了。

> 這就是為什麼 `from ultralytics import YOLO` 要寫在 `load_model()` 函式**裡面**，
> 不是寫在檔案最上面。放在最上面的話，`--preview-only` 也會被迫先載入 PyTorch ——
> 只想預覽畫面時也會被迫等模型套件載入。**import 寫在哪裡，會決定使用者啟動功能時要付多少成本。**

要邊飛邊辨識就用 `--every 10` 以上，但**飛行操控請用 `--preview-only`**。

## 3. 三條安全規則

> 第一節課**讀過就好、不用操作**（這節不飛）。但規則 1 跟 3 第一節就會遇到：
> 你如果好奇按了 `T`，會看到程式拒絕你；`Q` 離開時會看到它把串流收乾淨。

這三條不是文件裡的漂亮話，程式真的這樣做。

### 規則 1：起飛前必須先看到畫面

還沒收到任何一幀就按 `T`：

```
尚未看到畫面，取消起飛。沒有畫面等於盲飛。
```

**印訊息、中斷操作，不代勞。** 程式不會「順手幫你把串流打開然後起飛」——
起飛是不可逆的實體動作，不該是別的操作的副作用。

「前置條件沒滿足就自動幫使用者補齊」是很常見的貼心設計，但用在不可逆的實體動作上
就是災難。

### 規則 2：停止影像 / 降落 / 離開，是三件不同的事

| 按鍵 | 做什麼 | **不**做什麼 |
|---|---|---|
| 空白鍵 | 四軸速度歸零（懸停） | 不降落、不斷線 |
| `L` | 降落 | 不斷線、不離開程式 |
| `Q` | 離開程式（預設先降落） | — |

一個「停止」按鈕沒人說得清它停了什麼。使用者以為按了會降落，結果只是停止分析、
飛機還在空中 —— 那個誤解的代價是一台飛機。

### 規則 3：離開一定收乾淨

不管是 `Q`、`Ctrl-C` 還是程式炸掉，`finally` 都會走完：

```
rc 歸零 → 還在飛就降落 → streamoff → end()
```

**這一條和規則 1 看起來矛盾 —— 降落不也是程式擅自做的嗎？** 差別在**有沒有人看著**：
有 GUI 的程式關窗時可以彈窗問使用者，CLI 程式一結束就沒人控制飛機了 —— 懸停到電池
耗盡然後掉下來更糟。所以預設自動降落，要保留懸停得加 `--no-land-on-exit`
（然後你要自己接手）。

> 同一個原則（不要擅自做不可逆的事）在不同介面下導向不同結論。這就是為什麼要懂
> 原則，不是背規則。

### 另外：緊急停止預設沒有按鍵

`X` 鍵＝切斷馬達，機體會**直接墜落**。它只在加了 `--allow-emergency` 時才啟用 ——
一個會讓飛機掉下來的動作，不該是「手滑按到」就會發生的事。

## 4. 鍵盤

> 第一節課只會用到三個鍵：**`P` 拍一張、`Q` 離開、空白鍵**（不過這節不飛，空白鍵
> 沒事做）。下面整張表是選讀的飛行操控用的。

```
↑ ↓ ← →   前進 / 後退 / 左移 / 右移      8 2 4 6   同上（跨平台備援）
W / S      上升 / 下降                    A / D     左轉 / 右轉
空白鍵     全部歸零（懸停）                T / L     起飛 / 降落
P          拍一張                          Q         離開（會先降落）
X          緊急停止（需 --allow-emergency）
```

### ⚠️ 按一下會持續移動，放開不會停

`cv2.waitKey` 只有「按下」事件，**沒有「放開」事件**。所以做不到「按住才動、
放開就停」。這裡的速度會 latch 住：

**按 ↑ 之後它會一直往前飛，直到你按空白鍵或按 ↓。**

飛之前把這件事記牢。第一次實飛請用 `--speed 20`。

> 這是介面形式帶來的真實限制，不是偷懶。要做到「按住才動」需要一個有 key-up 事件的
> GUI 框架（PySide6、pygame 之類）—— 而這門課刻意不用 GUI 框架。
> **每個技術選擇都有代價，把代價講清楚比假裝沒有代價好。**

## 5. 程式碼導讀

### 段落 3：影像來源

```python
tello = Tello()
tello.connect()          # 沒回應會丟例外
tello.streamon()
frame_read = tello.get_frame_read()
```

連不上時的錯誤訊息刻意寫成兩條可行動的檢查，而不是丟一個原始例外給學生：

```
1. 電腦的 Wi-Fi 要連到 TELLO-XXXXXX 這個熱點
2. UDP 8889 沒被占用（另一個程式還開著就會占著）
```

**讀 frame 的兩個關鍵：**

```python
frame = frame_read.frame
if frame is None:
    return None
return cv2.cvtColor(frame, cv2.COLOR_RGB2BGR)
```

- djitellopy 的 frame 是 **RGB**（內部用 `frame.to_image()`），而 cv2 全家都吃
  **BGR**。不轉的話畫面顏色會反過來（天空變橘色），送進 YOLO 的張量也跟訓練時不
  一致，分數會怪。**這是最常見的「看起來能跑但結果怪」的 bug。**
- `frame_read.frame` 永遠是「**最新一格的快照**」，不是佇列。所以我們不用自己丟舊
  幀，延遲也不會累積 —— djitellopy 內部那條解碼執行緒幫我們做了這件事。
  `cv2.VideoCapture` 沒有這個性質，所以接 RTSP 之類的來源時得自己想辦法只留最新幀。

### 段落 7：主迴圈新增的三件事

**狀態列：每秒讀一次**

```python
if time.perf_counter() - last_state >= STATE_INTERVAL_S:
    state_text = f"電量 {tello.get_battery()}%　高度 {tello.get_height()} cm"
```

`get_battery()` 讀的是狀態封包的**快取**，不會送指令、不會阻塞。但也沒必要每幀都讀。

**rc 節流：每 50 ms 一次**

```python
if flying and (time.perf_counter() - last_rc) >= RC_INTERVAL_S:
    tello.send_rc_control(lr, fb, ud, yaw)
```

Tello SDK 建議 rc 指令不要超過 20 Hz。**灌太快會塞爆指令通道，反而讓起飛／降落
這類需要回應的指令被拖延** —— 實測灌到 125 Hz 就會出現這個現象。主迴圈本身跑得比
20 Hz 快得多，所以一定要節流。

**第一格畫面的等待有上限**

```python
if time.perf_counter() > first_frame_deadline:   # 10 秒
```

`streamon` 之後正常 2~3 秒就有畫面。等不到就印出可行動的訊息然後結束，
**不要無限等下去** —— 無限等待的程式看起來就像壞了。

## 7. 常見錯誤

| 訊息／現象 | 原因 |
|---|---|
| `連不上 Tello` | Wi-Fi 沒連到 `TELLO-XXXXXX`；或上一個程式還開著占住 UDP 8889 |
| `OSError: [WinError 10048]` | UDP 埠被占用。`netstat -ano -p UDP \| findstr 8889` 找出 PID 關掉 |
| 10 秒內沒有畫面 | 上一次沒關乾淨，UDP 11111 還被占。關掉所有 python 再試 |
| 畫面顏色很怪（天空是橘的） | RGB/BGR 沒轉。這章的 `read_frame()` 已經處理了 |
| 按 `T` 沒反應，印「取消起飛」 | 規則 1：還沒看到畫面。這是設計，不是 bug |
| 起飛失敗 | 訊息後面會印電量與溫度。多半是電量低或機身過熱 |
| 按鍵完全沒反應 | 焦點不在影像視窗上。用滑鼠點一下視窗 |
| 飛機一直往前飛停不下來 | **按空白鍵。** 這章的鍵盤是 latch 式的 |
