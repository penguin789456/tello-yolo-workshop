# Lab 3：整合 —— 操控 + 影像 + 拍照後辨識

> 檔案：`labs\lab3_detect.py`　需要 Tello EDU（`--source video` 可以沒有無人機）

把 lab1 的**操控**和 lab2 的**影像**接起來，再加上 YOLO 辨識。

## 1. 最重要的設計：辨識只在按下 `P` 的時候做

畫面以來源原本的速度跑（實測 Tello 約 20 fps），模型完全不介入。**只有你按下 `P`，
程式才對那一張跑一次 YOLO**，然後把標註圖和結果存下來。

### 為什麼不邊飛邊連續辨識

| 理由 | 數字 |
|---|---|
| 連續辨識會把畫面壓到個位數 fps | CPU 上 `yolo26n` 一張要 **50~60 ms** |
| 那個更新率沒辦法操控無人機 | 等你從畫面看到障礙物，早就撞上了 |
| 連續辨識還要多決定兩件事 | 門檻多高才算命中？多久存一次才不會塞爆硬碟？ |

所以規則很簡單：**你決定什麼時候辨識。** 按 `P` = 拍照 + 辨識 + 存檔，一次做完。

> 這是一個值得記住的取捨：**把「什麼時候做」交給使用者，程式就少掉一整組參數。**
> 連續辨識不是做不到，而是它帶來的複雜度（門檻、冷卻、丟幀）對這個場景不值得。

## 3. 模型要在主迴圈**之前**載好

```python
model, load_ms = load_model(args.weights)
```

**不要等第一次按 `P` 才載模型。** 實測載入 + warmup 要 3 秒 —— 那三秒飛機還在空中，
而你以為程式沒反應。

`warmup`（先跑一張假圖）同理：第一次推論要付 lazy 初始化的成本，實測第一張 89 ms、
後面每張 52 ms。把那個成本付在啟動階段。

## 4. 按下 `P` 之後發生什麼

整支程式唯一會跑模型的地方就是這個函式：

```python
def snap(model, frame, run_dir, conf, idx):
    dets, latency = detect(model, frame, conf)      # 1. 辨識
    overlay = draw(frame, dets)                     # 2. 畫框（不改原圖）
    path = save(run_dir, overlay, dets, ..., latency)  # 3. 存檔 + 寫索引
```

三步，照順序。注意 `draw()` 是**回傳新影像、不修改輸入** —— 主迴圈還要繼續用原始
那一張去顯示，標註版只是拿去存檔。

存出來的 `index.jsonl` 和 lab2 欄位一樣，只是現在真的有值了：

```json
{"file": "...snap000042.jpg", "label": "snap000042",
 "time": "2026-10-02T20:30:22", "count": 1, "best_score": 0.4412,
 "classes": ["bottle"], "latency_ms": 52.0}
```

## 5. 三條安全規則

程式真的這樣做，不是寫在文件裡好看的。

### 規則 1：起飛前必須先看到畫面

還沒收到任何一幀就按 `T`：

```
尚未看到畫面，取消起飛。沒有畫面等於盲飛。
```

**印訊息、中斷操作，不代勞。** 程式不會「順手幫你把串流打開然後起飛」——
起飛是不可逆的實體動作，不該是別的操作的副作用。

另外電量低於 30% 也不起飛，並且告訴你現在幾 %。

### 規則 2：降落 / 離開是兩件事

| 按鍵 | 做什麼 | **不**做什麼 |
|---|---|---|
| 空白鍵 | 四軸速度歸零（懸停） | 不降落、不斷線 |
| `L` | 降落 | 不斷線、不離開程式 |
| `Q` | 離開程式（預設先降落） | — |

### 規則 3：離開一定收乾淨

不管是 `Q`、`Ctrl-C` 還是程式炸掉，`finally` 都會走完：

```
rc 歸零 → 還在飛就降落 → streamoff → end()
```

**CLI 程式一結束就沒人控制飛機了**，所以預設會降落。要保留懸停得加
`--no-land-on-exit`（然後你要自己接手）。

> 這和規則 1 看起來矛盾 —— 降落不也是程式擅自做的嗎？差別在**有沒有人看著**：
> 有 GUI 的程式關窗時可以彈窗問使用者，CLI 沒有。
> **同一個原則在不同介面下會導向不同結論 —— 這正是為什麼要懂原則，不是背規則。**

### 另外：緊急停止預設沒有按鍵

`X` 鍵＝切斷馬達，機體會**直接墜落**。只在加了 `--allow-emergency` 時才啟用 ——
一個會讓飛機掉下來的動作，不該是「手滑按到」就會發生的事。

## 6. 鍵盤

```
P         拍照 + 辨識 + 存檔          Q        離開（會先降落）
T / L     起飛 / 降落                空白鍵    四軸歸零（懸停）
↑ ↓ ← →  前進 / 後退 / 左移 / 右移   8 2 4 6  同上（跨平台備援）
W / S     上升 / 下降                A / D    左轉 / 右轉
X         切斷馬達（需 --allow-emergency）
```

**按鍵要先用滑鼠點一下影像視窗取得焦點才有效。**

> ⚠️ 方向鍵是「按一下持續移動」，放開不會停 —— 要停請按**空白鍵**。
> `cv2.waitKeyEx` 的方向鍵回傳值不跨平台，程式裡寫的是 Windows 的值，
> 非 Windows 請用 `8 2 4 6`。

## 7. 動手改

1. **按 `P` 的時候同時存一張沒有框的原圖。** 想一下：檔名怎麼取才看得出配對關係？
2. **加 `--min-count N`**：偵測到的物件少於 N 個就不存檔。這和「按了 P 一定要存」
   有什麼衝突？你會怎麼處理（拒絕存還是存但標記）？
3. **寫一支 `report.py` 讀 `index.jsonl`**，印出：總共拍幾張、幾張有偵測到東西、
   每個類別各幾次、平均延遲。一行一筆的格式超好處理。
4. **把 `--conf` 降到 0.05 再按 `P`**，看它開始亂講話。記下最高分是多少 ——
   那個數字就是「它有多沒把握」。

## 8. 常見錯誤

| 訊息／現象 | 原因 |
|---|---|
| 按 `P` 之後要等三秒才有反應 | 模型沒在啟動時載好。檢查 `--no-model` 是不是忘了拿掉 |
| `拍一張 ... 0 處` | 畫面裡沒有 COCO 80 類的東西。這是正常的，見 [90-設計決策.md](90-設計決策.md) |
| 按 `T` 印「取消起飛」 | 規則 1：還沒看到畫面。這是設計，不是 bug |
| 飛機停不下來 | **按空白鍵。** 方向鍵是 latch 式的 |
| 按鍵完全沒反應 | 焦點不在影像視窗上，用滑鼠點一下 |
| 程式結束了但飛機還在空中 | 你加了 `--no-land-on-exit` |
